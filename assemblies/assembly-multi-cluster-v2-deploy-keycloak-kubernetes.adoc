= Deploying {project_name} for HA with the Operator (v2)




This {section} describes advanced {project_name} configurations for {kubernetes} which are load tested and will recover from single Pod failures or site failures.

These instructions are intended for use with the setup described in the link:{links_high-availability_multi-cluster-v2-concepts_url}[{links_high-availability_multi-cluster-v2-concepts_name}] {section}.
Ensure that the link:{links_high-availability_multi-cluster-v2-introduction_url}#multi-cluster-v2-infrastructure-requirements[{links_high-availability_multi-cluster-v2-introduction_name}] infrastructure requirements are met before proceeding.

While this blueprint uses {kubernetes}, the concepts are not limited to {kubernetes}.

== Prerequisites

* {kubernetes} clusters running. Each {kubernetes} cluster should have its own internal load balancing to leverage the startup, liveness and readiness probes of the {project_name} Pods.
* A load balancer in front of the clusters.
Each {kubernetes} cluster's ingress routes traffic to {project_name} Pods based on the `/health/ready` readiness probe, while the external load balancer probes `/lb-check` on each cluster to detect site-level failures.
* A highly available database deployed with synchronous replication across sites, reachable from all {project_name} nodes in all clusters.
The following example assumes a PostgreSQL database.
Any {project_name} supported database may be used provided that the selected database deployment can satisfy the required high-availability, synchronous-replication, consistency and latency characteristics. Database HA design and failover behavior are outside {project_name} and must be validated with the database vendor.
How to configure the database for high availability is out of scope for this guide.
* Understanding of a link:{links_operator_basic-deployment_url}[{links_operator_basic-deployment_name}] of {project_name} with the {project_name} Operator.

The following setup assumes a TLS passthrough setup, though this is not limited to this configuration.

== Procedure

Perform the following steps in each {kubernetes} cluster:

. Determine the sizing of the deployment using the link:{links_high-availability_multi-cluster-concepts-memory-and-cpu-sizing_url}[{links_high-availability_multi-cluster-concepts-memory-and-cpu-sizing_name}] {section}.
For this setup, you might see approximately twice the CPU usage and write IOPS on your database, though your results might vary based on your use case.

. Install the {project_name} Operator as described in the link:{links_operator_installation_url}[{links_operator_installation_name}] {section}.

. For a production-grade deployment, secure the database connection by creating a `ConfigMap` with the database certificate bundle:
+
[source,bash]
----
kubectl --namespace keycloak create configmap keycloak-db-rootcert --from-file db-ca.pem=/path/to/certificate.pem
----

. Deploy the {project_name} CR with the following values, using the resource requests and limits calculated in the first step:
+
[source,yaml]
----
include::../examples/generated/keycloak-stateless.yaml[tag=keycloak-stateless]
----
<1> Set the database URL.
<2> The database connection pool initial, max and min size should be identical to allow statement caching for the database.
The values shown are a starting point for production deployments; adjust to meet the needs of your system.
With the `stateless` feature, authentication sessions and action tokens are stored in the database, which increases database load compared to setups with an external {jdgserver_name} cluster. Adjust the pool size accordingly.
See the link:{links_high-availability_multi-cluster-concepts-database-connections_url}[{links_high-availability_multi-cluster-concepts-database-connections_name}] {section} for details.
<3> Specify the URL to your custom {project_name} image. If your image is optimized, set the `startOptimized` flag to `true`.
<4> Enable the `stateless` feature to remove the requirement for an external {jdgserver_name} cluster.
<5> Set a unique cluster name that identifies this cluster. Each cluster must have a distinct name; no two clusters may share the same name.
This option is only available if the `stateless` feature is enabled.
<6> To be able to analyze the system under load, enable the metrics endpoint.
<7> Secure the database connection. For non-production-grade environments without database TLS, set `db-tls-mode` to `disabled` in `additionalOptions` and omit the `truststores` block and the `keycloak-db-rootcert` `ConfigMap`.
<8> Specify the `ConfigMap` name that contains the database certificate bundle.
The Operator will automatically mount the file in the directory `/opt/keycloak/conf/truststores/configmap-<config map name>/<file-name>`.

IMPORTANT: Set `spec.hostname.hostname` to the same public URL on every site, and use either the same TLS certificate, or the same subject alternative name in the certificate.
This URL is the external load balancer's address that clients use to access {project_name}.
If the public URL uses a port other than 443, include the port in the hostname value (for example, `+https://auth.example.com:8443+`).

[#multi-cluster-v2-verify-deployment]
== Verify the deployment

Confirm that the {project_name} deployment is ready.

[source,bash]
----
kubectl wait --for=condition=Ready keycloaks.k8s.keycloak.org/keycloak
kubectl wait --for=condition=RollingUpdate=False keycloaks.k8s.keycloak.org/keycloak
----

To verify the hostname configuration, confirm that the OIDC issuer is identical on every site by querying each cluster's internal load balancer:

[source,bash]
----
curl -sk https://<SITE_LB_HOSTNAME>/realms/master/.well-known/openid-configuration | jq .issuer
----

Afterward, verify that the external load balancer routes traffic to both clusters.
The external load balancer should probe `GET /lb-check` on each cluster and expect an HTTP `200 OK` response to determine if a site is healthy.
When a site's {project_name} nodes are all unavailable, `/lb-check` will not return `200 OK`, and the load balancer should stop routing traffic to that site.
Kubernetes probes each Pod's `/health/ready` endpoint on management port 9000 and removes unready Pods from the Service endpoints, allowing the cluster ingress to avoid nodes affected by failures such as split-brain or loss of database connectivity.

[#multi-cluster-v2-sticky-sessions]
== Optional: Disable sticky sessions

When running on OpenShift and the default passthrough Ingress setup as provided by the {project_name} Operator, the load balancing done by HAProxy is done by using sticky sessions based on the IP address of the source.

The recommended way to run {project_name} behind a load balancer is to disable sticky session to allow for an even distribution of requests across all nodes.

Add the following supplementary configuration under the `spec` in the {project_name} Custom Resource to disable sticky sessions.

[source,yaml,subs="attributes+"]
----
spec:
  ingress:
    enabled: true
    annotations:
      # When running load tests, disable sticky sessions on the OpenShift HAProxy router
      # to avoid receiving all requests on a single {project_name} Pod.
      haproxy.router.openshift.io/balance: roundrobin
      haproxy.router.openshift.io/disable_cookies: 'true'
----
