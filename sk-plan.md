# Bridge Skills for sk-vale: Markdown-first agentic workflow

## Context

skupper-docs is authored in Markdown (Material for MkDocs). The ccs-ai-agentic-workflow plugins (docs-tools, cqa-tools) provide documentation review, writing, planning, and quality assessment — but their review/CQA skills target AsciiDoc. sk-vale already converts MD→AsciiDoc via kramdoc. Bridge skills in sk-vale can orchestrate: work in Markdown, convert when needed, invoke the ccs tooling, and trace findings back to source.

**Key discovery**: The ccs tooling already supports `--format mkdocs` for writing/planning. The gap is only on the review/CQA side, where structural checks require AsciiDoc.

**Goal**: Create skills in sk-vale that bridge the format gap, invokable alongside existing ccs plugins.

## Architecture decisions

### Local skills, not a plugin

Skills live in `sk-vale/skills/` (Claude Code auto-discovers these in the working directory).
- Invoked as `/skupper-review`, `/skupper-write`, etc. (no namespace prefix needed)
- The ccs plugins (docs-tools, cqa-tools) are installed separately and called by fully-qualified name from within these skills
- Can be promoted to a plugin later if needed

### Individual skills, no wayfinder

Direct invocation only: `/skupper-lint`, `/skupper-review`, `/skupper-write`, `/skupper-fix`, `/skupper-convert`, `/skupper-assess`.

## The trace-back mechanism

The critical piece: mapping AsciiDoc findings back to Markdown sources. 

`assembly-map.json` (already generated by `build_index.py`) provides the mapping:
```json
{
  "kube-yaml/site-configuration.md": "kube-yaml-assembly-kube-creating-site-yaml.adoc",
  "overview/security.md": "overview-assembly-skupper-security.adoc"
}
```

The namespace prefix convention (`kube-yaml-`, `overview-`) lets us map modules back too — modules inherit their assembly's prefix. A `traceback.py` script will:

1. Invert `assembly-map.json` → `adoc-name → md-path`
2. Use namespace prefixes to map modules to their source `.md` files
3. Match heading text to find approximate line numbers in the MD source
4. Output findings grouped by `.md` file


## Skills

### `/skupper-convert` — Pipeline wrapper
Runs `bash scripts/convert-skupper.sh --input-dir <path>`. Reports conversion status, number of modules/assemblies created. Other skills call this internally.

### `/skupper-lint` — Vale lint with traceback
1. Run `skupper-convert` (unless `--skip-convert`)
2. Parse `vale-report.json`
3. Run `traceback.py` to map findings to `.md` source files
4. Present findings grouped by MD file, not by AsciiDoc file
5. With `--fix`: open MD source and apply fixes

### `/skupper-review` — Full documentation review
1. Run `skupper-convert`
2. Run format-neutral style checks (Vale on MD directly, IBM SG language/grammar skills)
3. Run AsciiDoc structural review via `docs-tools:docs-review-style` on generated `.adoc`
4. Run `docs-tools:technical-reviewer` on MD source (it's format-agnostic)
5. Trace AsciiDoc findings back to MD via `traceback.py`
6. Consolidated report distinguishing: fixable-in-MD vs pipeline-level issues

### `/skupper-write` — Write new Markdown content
1. Read skupper-docs structure (mkdocs.yml nav, existing files for conventions)
2. Dispatch `docs-tools:docs-writer` agent with `--format mkdocs`
3. Write output to the correct location in skupper-docs/doc-input/
4. Auto-run `/skupper-lint` to validate

### `/skupper-fix` — Fix MD from Vale findings
1. Read `vale-report.json` from last conversion
2. Trace findings to MD source files
3. Categorize: directly fixable in MD / requires pipeline awareness / conversion artifact
4. Apply fixes to `.md` files following AGENTS.md patterns
5. Re-run conversion to verify

### `/skupper-assess` — CQA assessment
1. Run `skupper-convert`
2. Invoke `cqa-tools:cqa-assess` on AsciiDoc output
3. Trace findings back to MD sources
4. Report with MD-referenced findings

## Usage examples

### Direct skill invocation:
```
/skupper-lint                              # Lint all, trace to MD
/skupper-lint --file kube-yaml/custom-certs.md  # Lint one file
/skupper-review --style                    # Style review only
/skupper-review --tech                     # Technical review only
/skupper-write "TLS certificates guide"    # Write new MD content
/skupper-fix --rule ShortDescription       # Fix one rule type
/skupper-assess --scope full               # Full CQA assessment
```

### Composing with ccs skills:
```
# Use ccs directly after manual conversion
/skupper-convert
/cqa-tools:cqa-assess                     # Runs on fresh AsciiDoc

# Use docs-orchestrator with MkDocs format
/docs-tools:docs-orchestrator SKUPPER-1234 --format mkdocs

# Technical review directly on MD (format-agnostic agent)
/docs-tools:docs-review-technical

# Vale on MD natively (no conversion needed)
/docs-tools:lint-with-vale
```

### Multi-step workflow:
```
/skupper-plan "monitoring section for skupper console"
/skupper-write "monitoring section" --output-dir doc-input/console/
/skupper-review doc-input/console/monitoring.md
/skupper-assess --scope assembly
```

## Prerequisites

1. **Install ccs plugins** (for review/write/assess — lint and convert work without):
   ```
   claude plugin marketplace add git@gitlab.cee.redhat.com:ccs-ai/ccs-ai-agentic-workflow.git
   claude plugin install docs-tools@ccs-ai-agentic-workflow
   claude plugin install cqa-tools@ccs-ai-agentic-workflow
   ```
2. **skupper-docs** available as sibling directory (default: `../skupper-docs/doc-input`)
3. **Conversion tools** already installed: kramdoc, vale, python3, npm

## Verification

1. `/skupper-convert` — produces fresh modules/ and assemblies/
2. `/skupper-lint` — findings reference MD file paths, not AsciiDoc
3. `/skupper-review` — consolidated report with MD source references
4. `/skupper-write` — valid MkDocs MD in correct location, converts cleanly
5. `/skupper-fix` — fixes applied to MD, re-conversion shows fewer/zero findings
6. Cross-invocation: `/skupper-convert` then `/cqa-tools:cqa-assess` works directly
