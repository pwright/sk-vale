= Kafka SerDes integration

[role="_abstract"]
Contract rules can be evaluated during normal Kafka serialization and deserialization using the Apicurio Registry SerDes libraries. No code changes are required beyond configuration.

Enable contract rule evaluation by setting these properties on your Kafka producer or consumer:

.SerDes contract rule properties
[cols="3,1,3", options="header"]
|===
|Property |Default |Description

|`apicurio.registry.serde.contract-rules.enabled`
|`false`
|Enable contract rule execution during serialize/deserialize

|`apicurio.registry.serde.contract-rules.fail-on-error`
|`true`
|When `true`, any failed rule throws an exception, whatever its `onFailure` action. When `false`, violations are logged as warnings (`java.util.logging`) and processing continues

|`apicurio.registry.serde.contract-rules.cache.ttl.seconds`
|`60`
|How long the fetched ruleset is cached in the client

|`apicurio.registry.serde.contract-rules.migration.enabled`
|`false`
|Enable migration in the deserializer

|`apicurio.registry.serde.contract-rules.migration.target-version`
|None
|Target version for deserializer migration

|`apicurio.registry.serde.contract-rules.dlq.topic`
|None
|Topic that receives the records failing a rule with `onFailure: DLQ`. The serializer or deserializer sends them with a producer created from its own client configuration (bootstrap servers, security settings), then throws `ContractRuleViolationException`. Without this property, such a failure is an error
|===

Contract rule evaluation works as follows:

Rule source:: The SerDes fetch the global, artifact-level, and version-level rulesets of the schema version, merge their domain rules by name (the narrowest scope wins), cache them, and evaluate the rules locally in the client. Empty rulesets are cached too. A ruleset that cannot be fetched, for example because the registry is unreachable or refuses the request, is not cached: with `fail-on-error=true` the record is rejected, and the next record fetches the ruleset again.
Record conversion:: Avro generic records and JSON Schema records (`JsonNode` or a configured Java class) are converted to maps field by field: Avro enums and strings become strings, unions their value, bytes and fixed ISO-8859-1 strings, and logical types keep their underlying type (a `date` is an int). Protobuf messages are converted through their canonical JSON form (proto field names). Other records are converted by parsing the JSON output of their `toString()` method.
Producer (serializer):: Runs `WRITE` rules before serialization.
Consumer (deserializer):: Runs `READ` rules after deserialization.
Consumer migration:: With migration enabled and a target version set, a record written with another version is transformed by the migration rules on the path and returned as a record of the target version: an Avro `GenericRecord` built against the target version's schema (fields missing from the transformed record take their schema default, fields not in the schema are dropped), or JSON Schema data of the same type as read, validated against the target version's schema when validation is enabled. A transformed record that does not match the target schema is a migration failure. Records already at the target version, or with no migration rule on the path, are returned unchanged. Protobuf messages and Avro specific records (`apicurio.registry.use-specific-avro-reader=true`) are not migrated: the rules still run, but the record is returned as written and a warning is logged once.
Results:: The output of `TRANSFORM` domain rules replaces the record: the serializer writes the transformed record, and the deserializer returns the output of `READ` transforms. It is converted back to the record's type, as for migration: an Avro generic record of the schema, JSON Schema data of the same type, or a Protobuf message of the same type (Protobuf `READ` transforms keep the message type, so they apply even though Protobuf migrations do not). Avro specific records are written or returned unchanged.
Dead letter queue:: When a failed rule has `onFailure: DLQ`, the record (as serialized, or as read) is sent to the `dlq.topic` with the headers `apicurio.contract-rules.source-topic` and `apicurio.contract-rules.violations`, and a `ContractRuleViolationException` naming the topic is thrown, whatever `fail-on-error`: the record does not reach the original topic or the application. Other failures throw `ContractRuleViolationException` with `fail-on-error=true`, and are only logged with `fail-on-error=false`.

.Producer with contract rules example
[source,java]
----
Properties props = new Properties();
props.put(SerdeConfig.REGISTRY_URL, "http://localhost:8080/apis/registry/v3");
props.put(SerdeConfig.EXPLICIT_ARTIFACT_GROUP_ID, "my-group");
props.put(SerdeConfig.ARTIFACT_RESOLVER_STRATEGY, TopicRecordIdStrategy.class.getName());
props.put(SerdeConfig.CONTRACT_RULES_ENABLED, "true");
props.put(SerdeConfig.CONTRACT_RULES_FAIL_ON_ERROR, "true");
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, AvroKafkaSerializer.class.getName());
// ... other Kafka producer properties

KafkaProducer<String, GenericRecord> producer = new KafkaProducer<>(props);
----
