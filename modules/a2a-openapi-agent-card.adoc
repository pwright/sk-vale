= Auto-generating Agent Cards from OpenAPI specifications

[role="_abstract"]
If you already document your API with OpenAPI, you can embed Agent Card metadata directly in your OpenAPI specification's `info` block using the `x-agent-card` vendor extension, instead of authoring and maintaining a separate `AGENT_CARD` artifact by hand. {registry} detects the extension, assembles a valid Agent Card from it, and stores it as a companion artifact.

.Enabling OpenAPI-to-Agent-Card auto-generation
[cols="2,1,3"]
|===
|Property |Default |Description

|`apicurio.a2a.openapi-integration.enabled`
|`false`
|Auto-generate a companion AGENT_CARD artifact from the `x-agent-card` OpenAPI vendor extension

|`apicurio.a2a.openapi-integration.sync-on-update.enabled`
|`true`
|Update the generated Agent Card whenever its source OpenAPI artifact is updated
|===

NOTE: `apicurio.a2a.openapi-integration.enabled` is an experimental property. You must also set `apicurio.features.experimental.enabled=true` to use it.

.Example `x-agent-card` extension
[source,yaml]
----
openapi: "3.0.0"
info:
  title: Weather API
  description: Retrieves weather forecasts by city
  version: "1.0.0"
  x-agent-card:
    capabilities: {}
    skills:
      - id: get-weather
        name: Get Weather
        description: Retrieve the current weather for a city
        tags: [weather]
    defaultInputModes: [text]
    defaultOutputModes: [text]
servers:
  - url: https://weather.example.com
----

When {registry} publishes an OPENAPI artifact version with an `x-agent-card` extension under `info`, it:

. Derives any of `name`, `description`, and `version` that the extension does not explicitly set, from the OpenAPI document's own `info.title`, `info.description`, and `info.version`.
. Derives `supportedInterfaces` from `servers[]` only when omitted, expanding server variables using their string defaults and using `http+json` as the binding. Explicit malformed values are rejected rather than replaced. Relative URLs require explicit absolute `supportedInterfaces`; the registry does not guess a base URL. Publishers must ensure the advertised endpoint actually implements A2A; OpenAPI alone does not establish this.
. Validates the assembled Agent Card against the same A2A v1.0 schema used for `AGENT_CARD` artifacts. If the assembled card is not valid, the OpenAPI write itself is rejected (HTTP 400) with a `RuleViolationException`, and nothing is persisted.
. Creates or updates `<artifactId>-agent-card` in the same group, checking companion ownership and applying its configured rules. Companion failure is logged and leaves the successful source write intact; rejected companion content is never persisted.

Ordinary DRAFT creates/edits do not generate published companions. Transitioning a draft to a published state validates and generates from its edited content. Dry-run requests do not write companions. Published updates re-read the source tip, and conditional target-version writes prevent a concurrent manual version from being superseded.

Required Agent Card fields with no OpenAPI equivalent — `capabilities`, `skills`, `defaultInputModes`, and `defaultOutputModes` — must always be supplied explicitly in the extension.

.Provenance and sync labels
The companion artifact and its source OpenAPI artifact are marked with `apicurio.a2a.openapi-agent-card.*` labels:

[cols="2,3"]
|===
|Label |Meaning

|`apicurio.a2a.openapi-agent-card.generated` (on the companion)
|`true` if this artifact was generated by this feature

|`apicurio.a2a.openapi-agent-card.source-group-id` / `.source-artifact-id` (on the companion)
|Identifies the source OpenAPI artifact this companion was generated from

|`apicurio.a2a.openapi-agent-card.generated-hash` (on each generated companion version)
|Canonical hash committed with that generated content. Missing or mismatched provenance stops automatic synchronization.

|`apicurio.a2a.openapi-agent-card.source-global-id` (on each generated companion version)
|The exact source version; deletion/recreation of the source does not silently adopt the old companion.

|`apicurio.a2a.openapi-agent-card.artifact-id` (on the source OpenAPI artifact)
|The artifact ID of its generated companion Agent Card
|===

If you edit the generated Agent Card artifact directly, {registry} detects this the next time the source OpenAPI artifact changes (the companion's latest version content no longer matches its recorded generated hash) and skips the sync rather than overwriting your edit, logging a warning instead.

If an artifact already exists with the same name as the companion (`<artifactId>-agent-card`) but was not generated by this feature, {registry} leaves it untouched and logs a warning rather than overwriting it.

Labels are editable provenance/navigation hints, never authorization grants. Owner-only access is checked independently on the companion. Generation provenance is stored atomically with each version; failure updating the source navigation link can be repaired on a subsequent unchanged-content synchronization. A manually edited version without generation provenance is preserved. Regeneration after manual changes requires an explicit user decision, not deletion of its hash label.

[role="_additional-resources"]
.Known limitations
* REST publication paths trigger generation: first published version, new published version, `ifExists=UPDATE`/`FIND_OR_CREATE_VERSION`, and publication of an edited draft. KafkaSQL REST requests journal both writes; replay itself does not generate an extra companion. Confluent-compatible APIs and read-only GitOps/KubernetesOps imports do not trigger generation.
* Source and companion are separate artifacts, not one transaction. Companion errors leave the source intact; repeated optimistic conflicts are bounded and logged. A later publication retries from current source content.
* Deleting the source OpenAPI artifact does not delete its generated companion Agent Card.
* AsyncAPI does not currently support the `x-agent-card` extension.
