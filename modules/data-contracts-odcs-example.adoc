= ODCS contract example

[role="_abstract"]
Submitting a complete ODCS v3.1 contract to {registry} produces a set of projections on the schema artifacts that the contract references. The example contract and its resulting projections show how each contract section maps to labels and rules on those artifacts.

.ODCS v3.1 contract
[source,yaml]
----
apiVersion: v3.1.0
kind: DataContract
id: orders-contract
info:
  title: Orders Contract
  version: 1.0.0
  description: Data contract for order events
  status: active
  dataClassification: confidential
team:
  name: orders-team
  domain: commerce
  contact: orders@company.com
schemas:
  - name: OrderEvent
    type: avro
    location: orders/OrderEvent:3
    fields:
      customerEmail:
        description: Customer email address
        pii: true
        tags:
          - PII
          - EMAIL
      totalAmount:
        description: Total order amount in cents
quality:
  accuracy:
    - name: positive-amount
      expression: totalAmount > 0
      threshold: 1.0
    - name: valid-email
      expression: "customerEmail.matches('.*@.*\\\\..*')"
      threshold: 0.99
  completeness:
    - field: orderId
      threshold: 1.0
    - field: customerEmail
      threshold: 0.99
  freshness:
    maxStaleness: PT5M
serviceLevel:
  availability: 0.999
  latency:
    p99: PT1S
----

When submitted, this contract results in the following projections:

. An `ODCS_CONTRACT` artifact is created to store the YAML.
. Namespaced labels are set on the `orders/OrderEvent` artifact, for example `contract.orders-contract.status=STABLE`, `contract.orders-contract.owner.team=orders-team`, and `contract.orders-contract.classification=CONFIDENTIAL`.
. Two CEL contract rules are created: `odcs:orders-contract:positive-amount` with `onFailure=ERROR`, and `odcs:orders-contract:valid-email` with `onFailure=DLQ`.
. Completeness thresholds are stored as labels, such as `contract.orders-contract.quality.completeness.orderId=1.0`.
. Field tags are set on version 3: `field-tag.orders-contract:customerEmail|PII=EXTERNAL` and `field-tag.orders-contract:customerEmail|EMAIL=EXTERNAL`.
. SLA labels are stored for external monitoring tools.

When you update an ODCS contract with `PUT /groups/\{g}/contracts/\{contractId}`, a new contract version is added (re-submitting an existing `info.version` returns HTTP 409) and the contract is re-projected:

* The `contract.\{contractId}.*` labels taken from the YAML are replaced. The stage, compatibility group, and lifecycle dates set through the API are kept.
* The status from `info.status` is applied only if the contract lifecycle allows moving to it from the current status (see <<data-contracts-lifecycle_{context}>>). Otherwise the current status is kept, and the response contains a warning.
* Rules named `odcs:\{contractId}:*` are replaced; a version without `quality.accuracy` rules removes them. Other rules, such as rules added manually through the contract ruleset API, are preserved.
* Field tags are replaced on the target version; a version without field metadata removes them.
* Schemas the previous version referenced and the new version does not lose the contract's labels, rules, and field tags.

If a projection fails for any reason other than a missing schema artifact, an invalid location, or a missing version, the new contract version is deleted (or the new contract artifact, on a first submission), the contract's labels, rules, and field tags on every affected schema artifact are put back as they were before the request, and the request fails with HTTP 400. The cause is written to the server log.
