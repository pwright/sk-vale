= Token exchange delegation



[NOTE]
====
Token Exchange Delegation is
*Technology Preview*
and is not fully supported. This feature is disabled by default.


To enable start the server with `--features=preview` or `--features=token-exchange-delegation`

====

Token exchange delegation allows a subject (a user) to pre-authorize an actor (an administrator or a client application) to act on their behalf, as described in the https://datatracker.ietf.org/doc/html/rfc8693#name-delegation-vs-impersonation[delegation semantics of the token exchange specification].


**Why use delegation**


The specification describes two ways one party can act for another. Suppose Alice, the *subject*, wants a calendar app, the *actor*, to book meetings for her:

Impersonation:: The app gets a token that simply says "Alice". Her calendar service cannot tell whether Alice or the app made a booking.

Delegation:: The app gets a token that says "the calendar app, acting for Alice". The calendar service sees both names, and can log or restrict what the app does on her behalf.

{project_name} implements delegation, through the `may_act` and `act` claims.

Handing the user's own access token to the actor, whether that actor is another user or a client application, is impersonation in effect, and it has significant drawbacks:

* *No audience control.* Alice's token was issued to the app she logged in with, and its `aud` comes from that client's audience and role scope mappings. Nothing binds it to the calendar service, so the calendar app can present it to any other service that accepts it.
* *No scope restriction.* Alice's token carries everything she is allowed to do, not just booking meetings. If the calendar app is compromised, the attacker can use it anywhere Alice's token is accepted.
* *No audit trail.* The calendar service sees a request from Alice. It cannot tell the calendar app made it, so a misbehaving app looks exactly like her.
* *No user consent.* Alice is never asked whether the calendar app may act for her.

Delegation addresses all of these. The delegated token is issued with the audience and scopes of the requesting client, the client that performs the exchange, narrowing it to only what that client needs. In client delegation, the requesting client is the actor itself. The `act` claim provides a clear audit trail, and the user must explicitly consent to the delegation.


**Delegation types**


{project_name} supports two kinds of actor.

[cols="3*", options="header"]
|===
|Aspect |Admin delegation |Client delegation
s|Scope | `delegation:user:<username>` | `delegation:client:<client_id>`
s|Actor | A user, typically an administrator | A client application, through its service account
s|Use case | Administrator acts on behalf of a user | Application, such as an AI agent, acts on behalf of a user
s|`may_act` contains | `sub` (actor user ID) | `sub` (service account user ID) and `client_id`
|===


**Enabling delegation**


This feature requires the `parameterized-scopes` feature to be enabled. To enable both features, start {project_name} with:

[source,bash]
----
bin/kc.[sh|bat] start --features=token-exchange-delegation,parameterized-scopes
----

When the feature is enabled, the delegation client scopes (`delegation:user` and `delegation:client`) are automatically created in all realms (new and existing) as *Optional* client scopes, making them available to all clients by default. No manual client scope assignment is needed.

The client requesting a delegation scope must have *Consent required* enabled. The delegation scopes are marked as always requiring consent, and {project_name} rejects a request for such a scope from a client that does not require consent. The delegation consent is never stored permanently, so the user approves the delegation on every login session.

Delegation also requires granting a delegation permission through link:{adminguide_link}#_fine_grained_permissions[Fine-grained admin permissions version 2] (FGAP V2). Without a matching permission granting the `delegate` scope, the delegation scope is silently dropped from the request and the `may_act` claim is not included in the token. The login itself still succeeds.

NOTE: Delegation permissions require FGAP V2. FGAP V1 does not support delegation.


**Granting delegation permission**


Unlike impersonation, delegation does not use admin roles. Instead, you configure FGAP V2 permissions to control which actors can be delegated to and for which users.


**Granting delegation to all users**


This example allows the `actor-app` client, and only that client, to act on behalf of any user in the realm.

. Go to *Realm Settings* -> *Admin Permissions* and enable Admin Permissions.
. Navigate to *Admin Permissions*.
. Create a new permission on the *Users* resource type.
. Add the *delegate* scope.
. Under *Enforce access to*, leave *All users* selected. Those are the users that can be acted *for*.
. Under *Policies*, click *Create new policy*, choose *Client*, and select `actor-app`. The policy is the set of actors allowed to act, so only `actor-app` can delegate. Adding more clients to the policy widens that set.

If you want to restrict the permission to an administrator instead of a client, choose the *User* type for the policy in the last step, and select the administrator username.

With this in place, `scope=openid delegation:client:actor-app` succeeds for any user, while `delegation:client:some-other-app` is dropped during scope resolution.


**Granting delegation to members of a specific group**


. Navigate to *Admin Permissions*.
. Create a new permission on the *Groups* resource type.
. Add the *delegate-members* scope.
. Under *Enforce access to*, choose *Specific groups* and select the target groups.
. Under *Policies*, click *Create new policy*, or assign an existing one, targeting the administrator or service account allowed to delegate.


**Admin delegation**


Admin delegation allows a user (subject) to delegate their token to an administrator (actor). The client requests the `delegation:user` scope with the administrator's identifier as a parameter using the link:{adminguide_link}#_parameterized_client_scopes[parameterized scopes] syntax.


**How it works**


. The client requests the `delegation:user` scope with the administrator's (actor) username as a parameter, for example `scope=openid delegation:user:admin`. When the realm has *Login with email* enabled, the administrator's email can be used instead, for example `scope=openid delegation:user:admin@example.com`. For users in the built-in store, both lookups are case-insensitive. For users from a custom user storage provider, case sensitivity is determined by that provider.
. {project_name} validates that the named user exists, is not a service account, and is not the user who is logging in.
. {project_name} validates that the named administrator (actor) has the `delegate` permission for the user (subject) through FGAP V2.
. The user (subject) is presented with a consent screen to approve the delegation.
. If the user consents and validation passes, the issued token includes the `may_act` claim with the actor's user ID as the `sub`:
+
[source,json]
----
{
  "sub": "0fa1e5d4-3c2b-4a19-8765-0123456789ab",
  "may_act": {
    "sub": "f1234567-89ab-cdef-0123-456789abcdef"
  },
  "scope": "openid delegation:user:admin",
  ...
}
----

The `may_act` claim declares that the specified administrator (actor) is authorized to act on behalf of the user (subject). The `sub` inside `may_act` contains the actor's user ID, consistent with {project_name}'s standard `sub` claim semantics. An external Security Token Service (STS) receiving this token can verify the delegation authorization directly from the claim without querying back to {project_name}.

NOTE: Unlike `delegation:client`, the `delegation:user` scope does not add anything to the subject token's `aud` claim. If the administrator performs the exchange from a client other than the one the subject token was issued for, that client must still be within the subject token's audience. Add an *Audience* mapper to the subject client if that is not already the case.


**Adding additional claims to `may_act`**


By default, only the actor's `sub` (user ID) is included in the `may_act` claim. It is produced by the built-in *Parameterized Scope User Property* mapper named `may_act sub`, which resolves the scope parameter as a username (or an email, when the realm allows login with email) and maps that user's ID into the claim. Additional claims can be added by configuring extra *Parameterized Scope User Property* mappers on the `delegation:user` client scope in the Admin Console.

For example, to include the actor's username:

. Navigate to *Client scopes* -> *delegation:user* -> *Mappers* -> *Add mapper* -> *By configuration* -> *Parameterized Scope User Property*.
. Set *User Attribute* to `username`.
. Set *Token Claim Name* to `may_act.preferred_username`.
. Enable the token types where the claim should be included (e.g. access token, ID token).

The resulting token will then include:

[source,json]
----
{
  "may_act": {
    "sub": "f1234567-89ab-cdef-0123-456789abcdef",
    "preferred_username": "admin"
  }
}
----

Other useful claims to add include `may_act.email` (user attribute `email`) or `may_act.iss` (for cross-realm delegation scenarios).
