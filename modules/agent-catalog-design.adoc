= Agent catalog design

[role="_abstract"]
You can organize your agent cards in {registry} by using groups, naming conventions, and versioning strategies that support efficient discovery and lifecycle management.

**Group structure.** Organize agent cards into groups based on your organizational needs:

* **By team**: `team-alpha`, `team-beta`. Use this approach when teams own distinct sets of agents and you want clear ownership boundaries.
* **By capability**: `nlp-agents`, `vision-agents`, `data-agents`. Use this approach when you want to browse agents by functional area.
* **By environment**: `dev-agents`, `staging-agents`, `prod-agents`. Use this approach when you run separate agent registries per environment, or when you need to distinguish agent versions by deployment target.

**Agent card naming and versioning.** Use descriptive artifact IDs that indicate the agent purpose, such as `sentiment-analyzer` or `document-translator`. Include the version in the agent card content to distinguish between released versions.

Follow semantic versioning for agent cards:

* Increment the major version when you remove skills or change the agent URL.
* Increment the minor version when you add skills or capabilities.
* Increment the patch version for description or metadata updates.

**Agent lifecycle.** Manage agent cards through a defined lifecycle:

* **Draft**: an initial agent card in a development group (for example, `dev-agents/my-agent`), validated against {registry} validation rules.
* **Published**: a production-ready agent card in a production group (for example, `prod-agents/my-agent`). Other agents and orchestrators discover the agent through well-known endpoints.
* **Deprecated**: a disabled agent card version. Disabled versions are excluded from the `latest` branch and do not appear in search results that use default version resolution.

{registry} automatically extracts structured content from agent cards for search indexing. The following table lists the structured content key prefixes and their sources.

.Structured content taxonomy
[cols="2,3",options="header"]
|===
|Structured content key |Source in agent card

|`agent_card:skill:<id>`
|Each `id` value in the `skills` array

|`agent_card:capability:<name>`
|Each property name in the `capabilities` object where the value is `true`

|`agent_card:inputmode:<mode>`
|Each value in the `defaultInputModes` array

|`agent_card:outputmode:<mode>`
|Each value in the `defaultOutputModes` array

|`agent_card:protocolbinding:<binding>`
|Each `protocolBinding` value in the `supportedInterfaces` array

|`agent_card:securityscheme:<name>`
|Each key in the `securitySchemes` object

|`agent_card:tag:<value>`
|Each value in the `tags` array within each skill (deduplicated across skills)
|===

[NOTE]
====
Artifact-level structured content search is supported by `sql`, `kafkasql`, `gitops`, and `kubernetesops`. The index follows the latest published, non-disabled branch tip. Draft writes do not replace published entries; publication, disable/restore, deletion and imported versions/branches refresh the index transactionally.

Import populates the index without requiring re-upload. OpenAPI/AsyncAPI YAML is normalized to JSON before extraction. Full `type:kind:value`, partial `kind:value`, and plain `value` filters use case-insensitive exact value matching; SQL wildcard characters in partial kinds are treated literally. Blank components are rejected. Negated structure filters require a positive artifact-type constraint to avoid matching unrelated artifact families. Elasticsearch full-text/version-level search remains a separate feature.

Values are indexed using a SHA-256 equality key over the full lowercased value, not a truncated prefix. Long skill IDs sharing their first 256 characters therefore remain distinct. Live indexing, upgrade backfill and lookup use the same encoding; original values remain in artifact content. Empty or whitespace-only `skill`, `capability`, `inputMode`, and `outputMode` parameters return HTTP 400. Capability suffixes must be `:true` or `:false`.
====

[NOTE]
====
Database upgrade 110 backfills existing published content for built-in types with structured extractors, skipping no-op extractors. It follows the published branch tip, with a latest-published-version fallback when imported branch metadata is absent. Progress is logged every 500 artifacts. Plan for a one-time startup cost proportional to eligible content. Extraction errors are logged and counted; SQL failures abort the transaction instead of claiming a successful partially aborted write. Custom provider backfill requires a separately registered provider available to the upgrader.
====

Design your agent cards with consistent skill IDs and capability names across your organization. With consistent naming, discovery queries return accurate results. For example, use `translation` rather than `translate` or `translator` as the skill ID across all translation agents.
