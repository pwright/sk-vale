= Configuring the storage content cache

[role="_abstract"]
You can disable the storage content cache, change its size limit, or tune the staleness window for the content-and-type entry. {registry} reads these settings at startup, so you apply them by restarting {registry} with updated configuration properties or environment variables.

.Prerequisites
* {registry} is installed and you can change its configuration properties or environment variables.
* You can reach the {registry} management port, `9000` by default, to read metrics.

.Procedure
. Decide whether to keep the cache enabled. To disable it entirely, set `apicurio.storage.content-cache.enabled` to `false`. The default value is `true`.
. Set the per-cache size limit in bytes with `apicurio.storage.content-cache.max-size`. The default value is `67108864` (64 MiB). For example, set `134217728` to allow 128 MiB in each of the three caches.
. Set the staleness window for the content-and-type entry with `apicurio.storage.content-cache.hot-path.ttl-seconds`. The default value is `30`. Set `0` to disable that cache and query storage on every Confluent-compatible schema lookup by ID.
. Apply the settings and restart {registry}. Use configuration properties or the equivalent environment variables:
+
.Example: Configuration properties
[source,properties]
----
apicurio.storage.content-cache.enabled=true
apicurio.storage.content-cache.max-size=134217728
apicurio.storage.content-cache.hot-path.ttl-seconds=10
----
+
.Example: Environment variables in a container deployment
[source,yaml]
----
environment:
  APICURIO_STORAGE_CONTENT_CACHE_ENABLED: "true"
  APICURIO_STORAGE_CONTENT_CACHE_MAX_SIZE: "134217728"
  APICURIO_STORAGE_CONTENT_CACHE_HOT_PATH_TTL_SECONDS: "10"
----

.Verification
These steps assume the default setting `apicurio.ccompat.legacy-id-mode.enabled=false`.

. Request the same content twice by content ID. Replace `1` with a content ID that exists in your registry:
+
[source,bash]
----
$ curl -s http://localhost:8080/apis/registry/v3/ids/contentIds/1 > /dev/null
$ curl -s http://localhost:8080/apis/registry/v3/ids/contentIds/1 > /dev/null
----
. Read the cache metrics from the management port and filter for the content caches:
+
[source,bash]
----
$ curl -s http://localhost:9000/metrics | grep 'cache="content'
----
. Confirm the behavior that matches your configuration:
+
* When the cache is enabled, `cache_gets_total{cache="contentById",result="hit"}` increases on the second request and `cache_size{cache="contentById"}` is at least `1`.
* When the cache is disabled, the output contains no series with a `cache="contentById"`, `cache="contentByHash"`, or `cache="contentAndTypeById"` tag.
* When the TTL is `0`, the `cache="contentAndTypeById"` series are absent while the other two caches still report metrics.
