= Performing the delegated exchange


Once the subject's token carries a `may_act` claim, the actor performs the actual exchange at the token endpoint. This step is the same for admin delegation and client delegation. Only the contents of the `may_act` claim differ.

The `actor_token` is an ordinary access token belonging to the actor. {project_name} resolves the user behind it and treats the request as client delegation when that user is a service account, and as admin delegation otherwise. For client delegation, the actor client obtains the token for its own service account with the `client_credentials` grant:

[source,http]
----
POST /realms/myrealm/protocol/openid-connect/token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&
client_id=actor-app&
client_secret=XXXXX
----

For admin delegation, the actor token is the administrator's own access token, obtained through whichever flow they normally log in with.

The actor then sends both tokens: the subject's token as the `subject_token` and its own token as the `actor_token`. The actor client is confidential, so it authenticates itself on this request as well. The following example uses `client_secret_post`, but the other client authentication methods work too.

[source,http]
----
POST /realms/myrealm/protocol/openid-connect/token HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Accept: application/json

grant_type=urn:ietf:params:oauth:grant-type:token-exchange&
client_id=actor-app&
client_secret=XXXXX&
subject_token=eyJhbGci[...redacted...]&
subject_token_type=urn:ietf:params:oauth:token-type:access_token&
actor_token=eyJhbGci[...redacted...]&
actor_token_type=urn:ietf:params:oauth:token-type:access_token
----

The delegation flow uses the following parameters:

[cols="1,1,2", options="header"]
|===
|Parameter |Requirement |Value
|`grant_type` |Required |`urn:ietf:params:oauth:grant-type:token-exchange`
|`subject_token` |Required |The subject's access token, carrying the `may_act` claim
|`subject_token_type` |Required |`urn:ietf:params:oauth:token-type:access_token`
|`actor_token` |Required |The actor's own access token. Its presence is what selects the delegation flow
|`actor_token_type` |Required |`urn:ietf:params:oauth:token-type:access_token`
|`requested_token_type` |Optional |`urn:ietf:params:oauth:token-type:access_token`, which is both the default and the only supported value
|===

NOTE: Without the `actor_token` parameter, the request is handled as a standard token exchange, which rejects any subject token carrying a `may_act` or `act` claim.

{project_name} then validates both tokens following the https://datatracker.ietf.org/doc/html/rfc8693#section-4.1[delegation semantics of RFC 8693]. Unless stated otherwise, a failed check returns `400 Bad Request` with the `invalid_request` error and a description of what failed.

[cols="1,2", options="header"]
|===
|Check |Fails when
|The actor token is valid |The `actor_token` cannot be verified, or `actor_token_type` is not an access token type
|The requesting client is entitled to each token |For either token, the requesting client is neither the client the token was issued for nor within its audience. This check returns `403 Forbidden` with the `access_denied` error
|The subject and the actor differ |The `actor_token` resolves to the same user as the `subject_token`
|The subject token carries `may_act` |The claim is missing, or is not an object
|`may_act.iss` matches the realm |The claim carries an `iss` that is not this realm's issuer
|`may_act.sub` names the actor |The claim has no `sub`, or its `sub` is not the user resolved from the `actor_token`
|`may_act.client_id` matches, when present |The claim's `client_id` is not the client the `actor_token` was issued for, or is not the client making the request
|===

The delegated token is issued in a transient session, so no refresh token is returned and the token carries no session identifier. It contains the `act` claim built from the subject token's `may_act` claim.


**Restricting the `may_act` claim with a client policy**


The delegation client scopes enforce the permission check and the user consent before adding a `may_act` claim. A claim with that name can reach a token by other routes though, such as a *Hardcoded claim* protocol mapper set directly on a client. That claim never passed either check, yet the exchange endpoint would honor it.

The `may-act` client policy executor closes this gap. It re-validates any `may_act` claim it finds in a token response, whatever produced it: the issuer must match the realm, the `sub` must be an existing enabled user other than the token's own user, that user must hold the `delegate` permission, and the matching delegation scope must have been consented. Tokens without a `may_act` claim are untouched, and tokens that fail are rejected with `invalid_request`.

Configure it under *Realm settings* -> *Client policies* by adding the *may-act* executor to a profile and attaching that profile to a policy. All three options are off by default:

[cols="1,2", options="header"]
|===
|Option |Effect when switched on
|*Reject any may_act claim* |Rejects every token carrying a `may_act` claim, for clients that must never take part in delegation
|*Avoid permission check* |Skips the revalidation of the `delegate` FGAP permission. The `may_act` validity checks on `iss` and `sub` still apply
|*Avoid consent check* |The user's login consent is still enforced by the normal flows. What is dropped is catching a `may_act` that a protocol mapper added without the user ever consenting to that delegation
|===

NOTE: The executor runs on the token response of every grant type, but only acts when that response carries a `may_act` claim. That is the login and refresh responses where the claim is minted, not the exchange itself, since the delegated token carries `act` and not `may_act`. Combine it with the *grant-type* condition to narrow it further.


**Troubleshooting**


Delegation scopes fail safe. If the actor is not authorized, the scope is dropped during scope resolution and the login still succeeds, only without a `may_act` claim in the token.

[cols="1,2", options="header"]
|===
|Symptom |Likely cause
|Login succeeds, but the token has no `may_act` claim |The actor lacks the `delegate` permission, the username or client ID is misspelled, or the actor client has no service account
|The authorization request fails with `invalid_scope` |The requesting client does not have *Consent required* enabled
|The exchange fails with `invalid_request` |The actor does not match `may_act`, or the `may_act` claim is missing or malformed in the subject token
|The exchange fails with `access_denied` |The requesting client is outside the audience of the subject token or of the actor token
|===

A dropped scope is always logged on the server at the `WARN` level, with the reason:

----
Invalid scope parameter for 'delegation:client': Client 'actor-app' does not have service accounts enabled in realm 'myrealm'
----

Two constraints are easy to miss: `delegation:user` cannot name a service account, so use `delegation:client` for those, and neither scope can be requested twice with different values in the same request.
