= MCP tool visibility

[role="_abstract"]
MCP tool definitions are not subject to the `apicurio.agent.visibility` discovery filter described in
ifndef::service-registry-downstream[]
xref:getting-started/assembly-a2a-features.adoc#a2a-visibility-model_{context}[Agent visibility model].
endif::[]
ifdef::service-registry-downstream[]
xref:a2a-visibility-model_{context}[Agent visibility model].
endif::[]
This is a deliberate design decision, not a gap: filtering `/.well-known/mcp-tools` would only imply a protection that does not exist, because tool discovery returns exactly the tools the caller can already find through the core search API.

* `apicurio.agent.visibility` and its `apicurio.a2a.default-visibility` fallback apply only to Agent Card discovery (`GET /.well-known/agents`, and Agent Card entries in AI Catalog and ARD responses). They have no effect on MCP tool discovery.
* `GET /.well-known/mcp-tools`, the compatible-tools endpoint (`/.well-known/mcp-tools/\{groupId}/\{artifactId}/compatible`), and MCP tool entries in AI Catalog and ARD responses return every MCP tool that the caller is authorized to see, unfiltered by visibility.
* The visibility label is a discovery-only hint, not access control, for both agents and tools: callers can retrieve artifacts they are authorized to read directly through the core v3 API or find them through `/apis/registry/v3/search`, regardless of their visibility labels. Per-resource authorization, when enabled, still restricts access and search results. An MCP tool artifact can still carry an `apicurio.agent.visibility` label, but {registry} does not act on it when serving MCP tool discovery requests.
