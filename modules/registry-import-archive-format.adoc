= Registry import archive format

[role="_abstract"]
The administrative import operation accepts a ZIP archive of registry entities, including metadata and schema content.
An archive of schema files alone does not contain the metadata required for import.
You can use the version 3 archive format to prepare data outside {registry}.

.Archive entries
[cols="2,3",options="header"]
|===
|Entry pattern |Purpose
|`manifest-<timestamp>.Manifest.json`
|Export format and source system metadata. The archive must contain one manifest.
|`content/<hash>.Content.json`
|Content ID, content hash, canonical hash or artifact type, media type, and serialized references.
|`content/<hash>.Content.data`
|Raw schema or API bytes. Each content metadata file has a matching data file with the same name before the extension.
|`groups/<groupId>.Group.json`
|Group metadata.
|`groups/<groupId>/artifacts/<artifactId>/MetaData.Artifact.json`
|Artifact metadata, including the artifact type.
|`groups/<groupId>/artifacts/<artifactId>/versions/<version>.ArtifactVersion.json`
|Version metadata, including its global ID and the content ID that links it to a content entry.
|`groups/<groupId>/artifacts/<artifactId>/branches/<branchId>.Branch.json`
|Branch metadata and an ordered list of version strings.
|`rules/<ruleType>.GlobalRule.json`
|A global rule. Group exports exclude these entries.
|`groups/<groupId>/rules/<ruleType>.GroupRule.json`
|A group rule.
|`groups/<groupId>/artifacts/<artifactId>/rules/<ruleType>.ArtifactRule.json`
|An artifact rule.
|`groups/<groupId>/artifacts/<artifactId>/contract-rules/<name>.ContractRule.json`
|A contract rule. Each entry has a distinct name.
|`comments/<name>.Comment.json`
|A comment associated with a version's global ID.
|===

The entity type suffix, such as `.ArtifactVersion.json`, is case-sensitive.
The importer reads entity fields from the JSON body and processes entities in dependency order, independently of their order in the archive.
The default group uses `default` in archive paths and `null` for the `groupId` field in entity JSON.

.Core entity fields
[cols="1,3",options="header"]
|===
|Entity |Fields and relationships
|Manifest
|`exportVersion` identifies the archive format, for example, `3.0`. `systemVersion` identifies the source registry version, for example, `3.0.0`. Other fields include `systemName`, `systemDescription`, `exportedOn`, `exportedBy`, and `dbVersion`.
|Content
|`contentId` identifies the content entry. `contentType` describes the raw bytes. `contentHash` is the SHA-256 hash of the bytes followed by the UTF-8 `serializedReferences` string when references exist. The registry canonical hash uses canonical content bytes followed by the serialized references when present. For content without references, you can omit `canonicalHash` and supply `artifactType` so that the importer computes the canonical hash.
|Group and artifact
|`groupId` identifies the group. An artifact also has `artifactId` and `artifactType`. Metadata fields include `owner`, `createdOn`, `modifiedBy`, `modifiedOn`, `description`, and `labels`. Artifact metadata can also include `name`.
|Version
|`groupId`, `artifactId`, and `version` identify the version. `globalId` is unique across versions. `contentId` refers to a content entry. `versionOrder` records the numeric creation order within the artifact. `state` contains a version state such as `ENABLED`. Version metadata can also include `name`, `description`, `labels`, ownership, and timestamps.
|Branch
|`groupId`, `artifactId`, and `branchId` identify the branch. `versions` contains version strings in branch order. `systemDefined` identifies system branches, including `latest`. Ownership and timestamps describe the branch.
|===

Entity timestamps such as `createdOn` and `modifiedOn` use milliseconds since the Unix epoch.
The `serializedReferences` field contains a JSON-encoded string, not a JSON array.
Each reference includes `name`, `groupId`, `artifactId`, and `version`.
For content without references, omit this field or use `null`.

For content with references, always supply a `canonicalHash` that matches the registry's canonicalization and reference serialization. Do not rely on the automatic computation: the importer computes the hash from the canonical content bytes only, without appending the serialized references, so the computed value never matches the hash that the registry computes when it registers content with references. A registry export includes the stored canonical hashes.

An import preserves IDs by default.
The archive must use consistent content IDs, global IDs, and artifact coordinates across related entries, even when the import generates new IDs.
Branches require explicit branch entries; importing versions alone does not populate the `latest` branch.
